# Sinatra 教科書 執筆・レビューワークフロー

この文書は、Sinatra 教科書を一章ずつ執筆し、レビュー、修正、再レビューを経て完成させるための作業ルールです。FBC Press の共通ルールを前提とし、この書籍固有の進行方法を定めます。

## 正本となる文書

- `OUTLINE.md`: 書籍全体の構成、各章の主張、映画図鑑の仕様
- `STATUS.md`: 現在の進捗、確定事項、未解決事項、次の作業
- `docs/WRITING_AND_REVIEW_WORKFLOW.md`: 章単位の執筆・レビュー工程
- `docs/chapter-designs/chapter-XX.md`: 各章の執筆前設計
- `reviews/chapter-XX/`: 各章のレビューと修正記録
- `manuscript/`: 公開対象となる原稿
- サンプルアプリのコード: 本文の手順と一致する、その章終了時点の実装

会話履歴だけを仕様や進捗の記録場所にしません。作業単位が完了したら `STATUS.md` と関係する章別文書を更新します。

## 一章の作業サイクル

### 1. 執筆前設計

本文を書く前に `docs/chapter-designs/chapter-XX.md` を作り、次を確定します。

- この章の主張
- この章の学習ゴール
- 必要な前提知識
- 前章から受け取るもの
- 次章へ渡すもの
- サンプルアプリへ加える変更
- Network タブ、ログ、画面などで観察する対象
- 本文中へ組み込む短い確認、試行、言語化
- この章では扱わないこと
- 使用するコード、図、表、スクリーンショット
- 技術仕様を確認する一次情報

章設計が `OUTLINE.md` と食い違う場合は、本文を書き始める前にどちらを修正するか判断します。

### 2. 執筆

一度に複数章を書かず、原則として一章ずつ進めます。

- 原稿と、その章で使用するコードを同じ作業単位で変更する。
- 本文に掲載するコードと実際に動かすコードを一致させる。
- 章の手順を最初から実行し、その章終了時点のアプリが動くことを確認する。
- 観察、試行、言語化は必要な節の流れへ組み込み、独立した部末演習は作らない。
- 公式資料で確認できる事実を推測で確定しない。
- 使用する Ruby、Sinatra、Rack、Puma、Bundler のバージョンを基準に動作を確認する。

### 3. 初回レビュー

原則として、次の 6 つの立場すべてでレビューします。

1. FBC ベテランメンター
2. 技術書のベテラン編集者
3. Ruby・Sinatra・Rack に詳しい技術者
4. フロントエンドエンジニア
5. HTML/CSS・Ruby まで学習した初学者
6. FBC 卒業生の現役 Web エンジニア

各レビューは独立して行います。担当レビュアーは、対象章、対象コード、`OUTLINE.md`、章設計、FBC Press の共通ルールだけを読み、ほかのレビューファイルを参照しません。6 件すべてを書き終えてからレビュー統合へ進みます。

レビューは `reviews/chapter-XX/01-fbc-mentor.md` から `06-fbc-graduate.md` へ保存します。各ファイルには次を含めます。

- 総評
- 良い点
- `must`、`should`、`could` に分けた改善点
- 疑問点
- 具体的な修正案
- 次へ進めるかどうかの判定

重要度は次の基準で付けます。

- `must`: 技術的な誤り、初学者が進めない欠落、重大な教育上の問題
- `should`: 品質を大きく改善するため、原則として対応すべき問題
- `could`: 採用しなくても章の目的を達成できる任意の改善案

### 4. レビュー統合

`reviews/chapter-XX/review-summary.md` に 6 件の指摘を統合します。

- 同じ原因による指摘をまとめる。
- 意見が対立している箇所を明示する。
- 各指摘の採用、不採用、保留を決める。
- 修正の順序と影響するファイルを記録する。

判断の優先順位は次のとおりです。

1. 技術的な正確さ
2. 初学者の理解しやすさ
3. Web アプリケーションの基本を学ぶという本書の目的
4. 技術書としての自然さ
5. FBC カリキュラムとの接続
6. 発展性や洗練された実装

レビュー指摘は機械的にすべて採用しません。高度な設計が初学者の理解を損なう場合や、書籍の範囲を不必要に広げる場合は、理由を記録して採用しません。

### 5. 修正

`must` は原則としてすべて解決します。`should` と `could` は、採否と理由を `reviews/chapter-XX/changes.md` に記録します。

修正後には次を確認します。

- 原稿とコードが一致している。
- 章の最初から手順を実行できる。
- 修正によって前章との接続が壊れていない。
- 次章の前提を先取りしすぎていない。
- 採用しなかった指摘の理由が、本書の目的と読者に基づいている。

### 6. 再レビュー

修正版を `reviews/chapter-XX/second-review.md` で再レビューします。再レビューでは初回レビューを繰り返さず、次を重点的に確認します。

- 初回レビューの `must` が解決されている。
- 修正による新しい矛盾や不具合がない。
- 原稿、コード、画面、図版が一致している。
- 初学者が省略された手順を推測せず進められる。
- 前章からの接続と次章への前提が保たれている。

重大な問題が残る場合は再修正し、`second-review-01.md`、`second-review-02.md` のように番号を増やします。

### 7. 章の完了

次をすべて満たしたときだけ、その章を完了とします。

- 未解決の `must` がない。
- 原稿の手順どおりにコードが動く。
- 初学者レビューで進行不能となる箇所がない。
- その章終了時点のサンプルアプリの状態を確認できる。
- 次章の前提が整っている。
- 初回レビュー、統合結果、修正記録、再レビューが保存されている。
- `STATUS.md` に完了状況と次の作業が記録されている。

章を完了して次章へ進む前は、`../FBC_Press/CONTEXT_MANAGEMENT.md` の基準に従い、必要な情報がリポジトリへ保存されていることを確認してから `/compact` を実行します。

## レビュー担当ごとの責務

### FBC ベテランメンター

FBC の学習段階、前後のカリキュラム、初学者がつまずく箇所、提出課題へ知識を転用できるかを確認します。メモアプリの攻略記事にすることや、Rails の書き方へ無理に寄せることは求めません。

### 技術書のベテラン編集者

章の目的、説明順、前提知識、情報量、初出用語、重複、現在地の分かりやすさ、図・表・コード・スクリーンショットの役割を確認します。

### Ruby・Sinatra・Rack に詳しい技術者

Ruby コード、Sinatra の API と設定、Rack との関係、Bundler、method override、リダイレクト、ERB、エスケープ、バージョン差異を確認します。高度な実装へ置き換えるのではなく、初学者向けとして正確かを判断します。

### フロントエンドエンジニア

HTML の構造、フォーム部品、レイアウトとビューの責務、CSS、アクセシビリティ、画面遷移、出力文脈ごとの XSS 対策を確認します。

### HTML/CSS・Ruby まで学習した初学者

説明どおりに手を動かせるか、変更箇所が分かるか、省略を推測せず進めるか、用語や英語の負荷が高すぎないかを確認します。専門的な改善案より、理解できなかった箇所を具体的に記録します。

### FBC 卒業生の現役 Web エンジニア

受講時に必要だった説明、実務へ持ち出せる考え方、難易度、誤解されやすい簡略化、データベース設計や Rails への接続を確認します。

## 全章完成後の横断レビュー

章別レビューとは別に、全章完成後に次を確認します。

- 用語とコードスタイル
- 前後参照
- 映画図鑑の最終状態
- 難易度の上がり方
- 重複説明
- 図版とスクリーンショット
- リンクと参考資料
- OSS 技術書としての一貫性

章単位で十分な品質を確保しながら前進し、全体最適だけを理由に一章の執筆を止め続けないようにします。ただし、技術的な誤りや後続章の前提を壊す問題は解決してから次へ進みます。
