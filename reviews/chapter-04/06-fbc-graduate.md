# 総評

FBC 受講時に混乱しやすい「フォームの `name` が `params` のキーになる」「POST しただけでは保存されない」という点が、かなり明確に説明されています。第5章で保存へ進む前に、リクエストの観察を挟む構成は実務的にも大事です。

改善点は、章末コードの照合性と、一時的な `params.inspect` 実装の位置付けです。初学者は動いたコードをそのまま完成形だと思いやすいため、次章で置き換えることを強く残したいです。

# 良い点

- `GET /movies/new` と `POST /movies` の役割分担が明確。
- Network パネルの Payload / Form Data を確認させている。
- `content_type :text` にして、XSS 章前に HTML 出力へ進まない判断が良い。
- `POST` と保存の違いを説明している。
- `PATCH` / `DELETE` を第7章へ送り、章の範囲を広げていない。

# 改善が必要な点

## must

### `params.inspect` が第4章だけの足場であることを章末に明示する

- 問題: 章末の完成コードに `params.inspect` があるが、第5章で保存処理へ置き換える足場であることがコード近くにない。
- 問題になる理由: FBC の提出物で、フォーム送信後に値を表示するだけの状態を完成と誤解する可能性がある。
- 修正案: 4.8 の `post "/movies"` の直後に、第4章だけの確認用で、第5章で保存とリダイレクトに置き換えると明記する。
- 対象箇所: 4.8

## should

### 章末に `views/index.erb` と CSS の差分を足す

- 問題: 導線と見た目の変更が章末で確認できない。
- 問題になる理由: 実務でもフォームは画面導線とセットで確認する。登録画面への入口がないと機能にたどり着けない。
- 修正案: `views/index.erb` 完成コード、または第4章で追加したリンク部分と CSS を掲載する。
- 対象箇所: 4.8

### Form Data と `params` の順序は保証しない方がよい

- 問題: `params.inspect` の表示例が固定の順序に見える。
- 問題になる理由: 固定バージョンでは実測どおりでも、読者は順番まで意味があると思う可能性がある。
- 修正案: 「表示順は重要ではなく、キーと値が届いていることを見る」と補足する。
- 対象箇所: 4.5

## could

### `POST` は安全という誤解をもう少し潰す

- 改善案: `POST` は URL に値が見えにくいが、Network パネルでは送信内容を確認できるため、秘密にできるわけではない、と短く補足する。
- 期待される効果: 「POST なら安全」という誤解を早めに防げる。
- 対象箇所: 4.2 または 4.6

# 疑問点

- 第4章では CSRF へ触れない判断でよい。範囲が広がりすぎる。
