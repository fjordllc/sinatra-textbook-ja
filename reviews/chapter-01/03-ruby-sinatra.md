# 総評

HTTP の説明は、後で Sinatra のルートへ対応付けるための前提として正確です。HTTP/1.1 のテキスト表現を教材上の例として使い、HTTP/2 以降の転送形式と HTTP の意味を分けているため、「現在の HTTP は常にその文字列が流れる」という誤解も避けています。固定した Ruby・Sinatra・Rack の構成は実機検証されており、偶然インストールされた Erubi などにも依存していません。

# 良い点

- ブラウザが Ruby のソースコードを受け取るのではなく、サーバー側の処理結果を受け取ると明示している。
- URL のパスとサーバー上の物理ファイルを同一視していない。
- HTTP メソッド、パス、ステータスコード、ヘッダー、本文の区別が正しい。
- `Content-Type` と HTML 本文の関係を、最小のレスポンス例で説明している。
- Ruby 4.0.6、Sinatra 4.2.1、Rack 3.2.6、Puma 8.0.2 がロックされ、method override、303、ERB エスケープまで検証されている。
- 第1章では Rack や Sinatra の内部 API へ踏み込まず、次章へ残している。

# 改善が必要な点

## must

### 404 が必ず返るように読める断定を修正する

- 対象: `manuscript/part1/chapter1.md:109`
- 問題: 「存在しないページへアクセスしたときには 404 が返る」と断定していますが、アプリケーションが誤って 200 を返すことも、別ページへリダイレクトすることも技術的には可能です。
- 理由: ステータスコードは資源の状態から自動的に決まるものではなく、サーバー側が適切に返す必要があります。第10章で実装する内容とも関係します。
- 修正案: 「見つからないことを伝える適切なレスポンスは `404 Not Found` です。映画図鑑でも第10章で明示的に返します」とする。

### 第1章時点のコード状態を原稿と一致させる

- 対象: `manuscript/part1/chapter1.md:147`, `app.rb:1-13`, `README.md:33-39`
- 問題: 原稿は「この章では、まだコードを書きません」としていますが、リポジトリにはリダイレクトと `/movies` ルートを持つ `app.rb` があります。
- 理由: 章の手順とサンプルコードを一致させるというプロジェクトの完了条件を満たしません。読者がリポジトリを見ると第2章の答えが先に存在します。
- 修正案: 第1章完了時点では `app.rb` を置かず、第2章で原稿と同時に追加する。技術検証は `scripts/verify-stack.rb` に残す。README の起動案内も第2章で追加する。

## should

### URL のスキーム説明を限定する

- 対象: `manuscript/part1/chapter1.md:42`
- 問題: 「通信に使う方法」は概ね分かりやすい一方、`file` もスキームであり、必ずしもネットワーク通信を表すわけではありません。
- 理由: 直前に `file://` と `http://` を対比しているため、説明の差が見えた方が正確です。
- 修正案: 「URL をどの仕組みで扱うかを表す。`http` は HTTP、`file` は手元のファイルを示す」と補う。

## could

### HTTP 例が簡略化されていることをコード直前にも示す

- 対象: `manuscript/part1/chapter1.md:76`
- 改善案: 「実際にはほかのヘッダーも含まれます」と短く添える。
- 期待される効果: Network パネルに多数のヘッダーが現れても、例と違うことを異常だと考えにくくなる。
