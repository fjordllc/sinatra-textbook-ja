# レビュー統合

## 対象

第8章「リダイレクトは二つのリクエストをつなぐ」

## 総評

6 観点すべてで、章の目的と構成は妥当と判断された。未解決の `must` はない。第5章から使ってきたリダイレクトを PRG として意味付けし、登録・更新・削除を Network タブと Sinatra ログで観察する章になっている。

## must

なし。

## should

- 比較コードは写す必要がなく、完成コードへ残さないことを明確にする。採用。
- PRG の名前と、PATCH/DELETE でも同じ考え方として扱うことを早めに説明する。採用。
- 更新・削除の図は設計上の見取り図であり、Network タブでは POST と `_method` として見えることを注記する。採用。
- Network タブでリダイレクト前後を追いやすいよう、Preserve log を補足する。採用。
- 再実行されていないことの判断材料として、JSON 件数や Sinatra ログを見ることを補足する。採用。
- PRG を再読み込み対策だけでなく、状態変更と表示の責務分離としても説明する。採用。

## could

- 303 以外のリダイレクトステータス比較は採用しない。本章の目的から外れるため。
- 図版やスクリーンショットは採用しない。現時点ではテキストと Network タブの観察で十分であるため。
- フラッシュメッセージは採用しない。PRG 後の通知として自然だが、本書の範囲を広げるため。

## 対応後の確認観点

- 完成コードに残す変更がないことが明記されていること。
- Network タブと Sinatra ログの見え方の違いが本文に残っていること。
- 第9章へ進む前提として、表示される値が利用者入力であることへ自然につながること。
