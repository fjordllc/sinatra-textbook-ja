# 総評

章の目的は明確で、文字列、HTML 文字列、ERB、レイアウト、Ruby データ、CSS という順序は初学者にとって追いやすい構成です。各節で「何が前より良くなったのか」が説明されており、単なる Sinatra 機能紹介にはなっていません。

改善点は、章内の段階的なコードと章終了時点のコードを区別する編集上の整理です。現状でも読めますが、章末の照合作業を支える情報が足りず、読者が途中のスニペットを組み合わせる必要があります。

# 良い点

- 冒頭に章のゴールが一文で示されている。
- 3.1 で直接 HTML 文字列を書く読みにくさを体験させてから ERB へ進む流れが自然。
- ERB の `<% %>` と `<%= %>` の説明をこの章で必要な範囲に絞っている。
- 一覧画面に全項目を出さない理由が、画面の役割として説明されている。
- 3.9 で HTML と CSS を Network パネルで観察させ、HTTP の観察を継続できている。

# 改善が必要な点

## must

### 章終了時点のファイル構成と完成コードが不足している

- 問題: 3.10 の表はファイルの役割を整理しているが、章終了時点の全ファイルの中身を確認できない。
- 問題になる理由: 章内で段階的に `layout.erb` や CSS にクラスを足しているため、読者は最終的にどの状態が正しいのか迷いやすい。
- 修正案: 3.10 にファイル構成を再掲し、`views/layout.erb`、`views/index.erb`、`public/stylesheets/application.css` の完成コードを追加する。少なくとも `layout.erb` と `index.erb` は必須。
- 対象箇所: `manuscript/part2/chapter3.md` 3.10

## should

### 3.6 の見出しと本文の関係を整える

- 問題: 見出しは「5 つの入力項目」だが、直後の表は `id` を含む 6 属性を説明している。
- 問題になる理由: 「映画は 5 つなのか 6 つなのか」という余計な認知負荷が生まれる。
- 修正案: 見出しを「映画は最初から 6 つの属性を持つ」などへ変更し、その中で利用者が入力するのは 5 項目だと説明する。
- 対象箇所: 3.6、章設計 3.6

### 初出用語 `静的ファイル` の説明は良いが、`静的な HTML` と混同しやすい

- 問題: 3.4 の「静的な HTML」と 3.7 の「静的ファイル」が近い章内に出てくる。
- 問題になる理由: 初学者は「静的な HTML」と「public 配下の静的ファイル」を同じ意味で捉える可能性がある。
- 修正案: 3.7 で「ここでいう静的ファイルは、Sinatra のルートで組み立てず、そのまま返すファイルのこと」と補足する。
- 対象箇所: 3.7

## could

### 3.1 の長い HTML 文字列例はもう少し短くてもよい

- 改善案: 読みにくさを示す例としては十分なので、現在のままでもよいが、初学者が写経するコードではないことを明記するとさらに親切。
- 期待される効果: 読者が一時例を最終コードに残す誤解を防げる。
- 対象箇所: 3.1
