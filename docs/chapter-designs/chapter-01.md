# 第1章 章設計

## 基本情報

- 章タイトル: Web アプリケーションはどこで動いているのか
- 対応する OUTLINE: `OUTLINE.md` 第1章
- 状態: 執筆開始可能

## この章の主張

Web アプリケーションはブラウザに表示された画面そのものではなく、ブラウザからのリクエストを受け取ったサーバーがレスポンスを返す仕組みです。ブラウザが受け取るのは Ruby のコードではなく、HTTP レスポンスだからです。

## 学習ゴール

ブラウザ、サーバー、リクエスト、レスポンスの関係を、図と Chrome DevTools の Network タブに表示される情報を使って説明できる。

## 読者が持ち帰る一文

ブラウザに見えている画面は、サーバーから返されたレスポンスをブラウザが解釈した結果である。

## 必要な前提知識

- HTML ファイルをブラウザで開いた経験がある。
- URL を入力して Web ページへアクセスできる。
- Ruby の基本文法を学習済みであるが、この章では Ruby コードを書かない。
- Chrome を利用できる。Firefox などにも同等の開発者ツールがあることは短く補足する。

## 前章から受け取るもの

前章はありません。本書の想定読者、映画図鑑を最後まで作ること、本書が Sinatra の網羅的な解説ではないことを「はじめに」で共有している前提です。

## 次章へ渡すもの

- URL、HTTP メソッド、ステータスコード、ヘッダー、レスポンス本文という観察項目
- `/movies` はファイル名ではなく、サーバーへ処理を依頼する宛先になり得るという理解

第2章では、この全体像のサーバー側を Sinatra で実際に作ります。

## サンプルアプリへ加える変更

この章では映画図鑑のコードをまだ作りません。映画図鑑の目的と画面構成を紹介し、次章から作る URL の例として `/movies` を示します。

コードを作らない理由は、Sinatra の書き方を先に見せると、読者が `get` やブロックの意味を追うことに集中し、ブラウザとサーバーの関係を捉えにくくなるためです。

## 章の中心となる理解

### ブラウザとサーバーの役割

- ブラウザは、URL が示す宛先へリクエストを送るクライアントである。
- サーバーは物理的な機械だけを指す言葉ではなく、リクエストを待ち受けてレスポンスを返すプログラムを指す場合がある。
- Web アプリケーションはサーバー側でリクエストを処理し、レスポンスを作る。
- ブラウザは Ruby や Sinatra のコードを受け取らず、主に HTML などを含むレスポンスを受け取る。

### URL はファイル名とは限らない

- ローカルの HTML ファイルを直接開く場合と、`https://.../movies` へアクセスする場合を対比する。
- `/movies` というパスが `movies.html` というファイルの存在を意味するとは限らない。
- どの処理を行うかは、サーバー側のルーティングが決める。ルーティングという用語は短く予告し、実装は第2章で扱う。

### リクエストとレスポンス

- リクエストには、宛先、HTTP メソッド、ヘッダーなどが含まれる。
- レスポンスには、ステータスコード、ヘッダー、本文などが含まれる。
- GET、200、404 はこの章では観察対象として紹介し、詳細な使い分けは後続章へ残す。

### HTTP メッセージの例

HTTP/1.1 の簡略化したリクエストとレスポンスを対で示します。

```http
GET /movies HTTP/1.1
Host: localhost:4567
Accept: text/html
```

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<h1>映画図鑑</h1>
```

この例では、次の対応だけを読み取ります。

- `GET`: 何をしてほしいかを表す HTTP メソッド
- `/movies`: リクエストの宛先となるパス
- `200 OK`: リクエストが成功したことを表すステータス
- `Content-Type`: レスポンス本文の種類
- `<h1>映画図鑑</h1>`: ブラウザが解釈するレスポンス本文

HTTP/2 と HTTP/3 は通信時の内部表現が異なることを注記で一文だけ補います。バージョン差の説明へは広げません。Chrome の Network タブが表示する内容は、通信内容を人が確認しやすい形へ整理した情報であり、通信バイト列そのものではないことにも深入りしません。

### 静的な HTML との違い

- HTML ファイルを直接開く場合も、ブラウザは HTML を解釈して画面を表示する。
- Web サーバーが静的な HTML ファイルを返す場合もあるため、「静的な HTML は Web ではない」とは説明しない。
- 本書で作る映画図鑑では、リクエストに応じて Sinatra が処理を選び、保存データから HTML レスポンスを作る。この点が単にファイルを直接開く場合と異なる。

## 節ごとの展開

### 1.1 ブラウザだけでは映画図鑑は動かない

完成後の映画図鑑で、一覧を見る、登録する、編集するという操作を短く示します。画面だけを見ても、データを保存する処理がどこで動くかは分からない、という問いから始めます。

### 1.2 URL はファイル名ではなくリクエストの宛先

ローカルファイルのパスと Web の URL を対比します。`/movies` を `movies.html` と結びつける必要はなく、サーバーが処理を割り当てられることを説明します。

### 1.3 リクエストとレスポンスの往復

ブラウザ、Web アプリケーション、レスポンスの往復を図で示します。ブラウザから送る矢印をリクエスト、戻る矢印をレスポンスとします。

### 1.4 HTTP のメッセージをテキストとして読む

簡略化した HTTP/1.1 の例を使い、メソッド、パス、ステータスコード、ヘッダー、本文を対応付けます。プロトコルという言葉は「通信するときの取り決め」と短く定義します。

### 1.5 静的な HTML と Web アプリケーションの違い

ブラウザが最終的に HTML を解釈する点は共通している一方、HTML を誰がどのように用意するかが異なることを説明します。「HTML か Web アプリケーションか」という誤った二分法にしません。

### 1.6 本書で作る映画図鑑の範囲

一覧、詳細、登録、編集、削除を持つ映画図鑑を紹介します。ログイン、画像、外部 API、データベースを扱わないことも短く示し、読者が完成形の大きさを把握できるようにします。

### 1.7 Network タブで最初に見るもの

ブラウザで開いている本書のページを対象に、Chrome DevTools の Network タブを開いて再読み込みします。`document` に相当するリクエストを選び、次を確認します。

- Request URL
- Request Method
- Status Code
- Request Headers
- Response Headers
- Response または Preview に表示される本文

この時点では各ヘッダーを暗記させません。ブラウザが画面の裏でリクエストを送り、レスポンスを受け取っていることを、実際の情報から確認するのが目的です。

## 先回りして防ぐ誤解

- Web アプリケーションはブラウザの中だけで動いている。
- URL のパスは、サーバー上の同名ファイルを表している。
- ブラウザが Ruby コードを受け取って画面を作っている。
- 静的な HTML は HTTP と関係がない。
- Network タブに表示される項目を最初からすべて理解しなければならない。
