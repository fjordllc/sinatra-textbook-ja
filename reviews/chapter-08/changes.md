# 修正記録

## 対応した指摘

### 比較コードを写さない注意

- 対象レビュー: `01-fbc-mentor.md`
- 対応: 直接 HTML を返す比較コードは説明のための例であり、写す必要はないと追記した。
- 理由: 初学者が完成コードを書き換えて戻せなくなることを防ぐため。

### PRG と PATCH/DELETE の関係

- 対象レビュー: `02-technical-editor.md`, `03-ruby-sinatra.md`
- 対応: PRG の名前は Post/Redirect/Get だが、本章では状態変更後に表示用 GET へ移る設計として扱うと早い位置へ移した。更新・削除では Network タブ上は POST と `_method` として見えることも注記した。
- 理由: 「PATCH/DELETE なのに PRG なのか」という混乱を避けるため。

### Preserve log の補足

- 対象レビュー: `04-frontend.md`
- 対応: Network タブでリダイレクト前後を見失う場合は Preserve log を有効にすると追いやすいと追記した。
- 理由: 初学者が画面遷移後に最初の POST を見失わないようにするため。

### 再実行されていないことの確認方法

- 対象レビュー: `05-beginner.md`
- 対応: 登録後は JSON の件数が増えないこと、更新後はログに PATCH が増えないこと、削除後はログに DELETE が増えないことを補足した。
- 理由: 画面が同じに見えるだけでなく、事実から判断できるようにするため。

### PRG の責務分離としての意味

- 対象レビュー: `06-fbc-graduate.md`
- 対応: POST/PATCH/DELETE はデータを変えるため、GET は結果を表示するための処理として役割を分けると追記した。
- 理由: PRG を再読み込み対策だけに見せず、Web アプリケーション設計として理解できるようにするため。

## 採用しなかった指摘

### リダイレクトステータスの詳細比較

- 理由: 第8章では `303 See Other` を現在の固定環境で観察できる事実として扱う。302、307、308 の詳細比較は本筋から外れるため採用しない。

### 図版やスクリーンショット

- 理由: 既存のテキスト説明と Network タブでの観察手順で章の目的は達成できるため、現時点では採用しない。

### フラッシュメッセージ

- 理由: PRG 後の通知として自然だが、セッションや表示設計へ範囲が広がるため採用しない。

## 新たな設計判断

- 第8章ではコード変更を残さない。第7章までの完成コードを使って、既存のリダイレクトの意味を観察・言語化する章とする。
