# キャプチャ制作リスト

## 目的

キャプチャは、本文を装飾するためではなく、読者が次の三つを迷わず確認できるようにするために使います。

1. 今、ブラウザや DevTools のどこを見ているのか。
2. 操作の前後で何が変わったのか。
3. 本文で説明している URL、HTTP メソッド、ステータスコード、フォームの値が画面上のどこに現れるのか。

コード、コマンド、ログを読ませることが目的なら、画像ではなく本文のコードブロックを使います。キャプチャは、画面上の位置関係や複数の情報の対応を見る必要がある場面に限ります。

## 優先度 A: 初学者が迷わないために必要

### 1. Network パネルで最初に見る三項目

- 掲載位置: 第1章「1.7 Network パネルで往復を確かめる」
- 撮影対象: 本書のページを再読み込みし、文書リクエストを選択した Network パネルの `Headers`
- 画面に含めるもの: リクエスト一覧、選択中の行、`Request URL`、`Request Method`、`Status Code`
- 伝えること: 読者が最初に選ぶ行と、最初に読む三項目の場所
- 注釈: 三項目を 1、2、3 の番号で示す。ヘッダー全文へ印を付けない
- 理由: DevTools を初めて使う読者は、項目名が分かっても、一覧からどの行を選ぶかで迷いやすい

### 2. リダイレクトで二つの GET が発生する様子

- 掲載位置: 第2章「2.10 Network パネルで二つの GET を見る」
- 撮影対象: `GET /` のリダイレクト後に `GET /movies` が発生した Network パネル
- 画面に含めるもの: `/` の 302、`/movies` の 200、`Headers` の `Location: /movies`
- 伝えること: `redirect` は移動先の本文を直接返すのではなく、ブラウザへ次のリクエストを促すレスポンスであること
- 注釈: 一覧の二行を矢印で結び、「1. 302」「2. GET /movies」と順序を示す
- 理由: 本文だけでは、ブラウザが二度リクエストしている感覚を持ちにくい

### 3. HTML と CSS は別々に取得される

- 掲載位置: 第3章「3.9 Network パネルで HTML と CSS を見る」
- 撮影対象: 映画一覧を開いた直後の Network パネル
- 画面に含めるもの: `movies` の document 行と `application.css` の stylesheet 行、Type、Status
- 伝えること: 一つの画面を表示するときも、HTML と CSS は別の URL へ別々にリクエストされること
- 注釈: document と stylesheet の二行だけを囲む
- 理由: `public/`、HTML、CSS、ブラウザ表示の関係を画面上の事実として結び付けられる

### 4. 登録フォームの完成状態

- 掲載位置: 第4章「4.4 映画の登録フォーム」
- 撮影対象: `GET /movies/new` の登録画面
- 画面に含めるもの: アドレスバー、タイトル、監督、公開年、ジャンル、紹介文、登録ボタン
- 伝えること: この章で作る画面の完成像と、これからコードに書く各フォーム部品の対応
- 注釈: 原則なし。必要ならキャプションで URL を示す
- 理由: 長いフォームコードを書く前に完成像が見えると、読者が現在地を保ちやすい

### 5. フォームの入力値が Form Data になる

- 掲載位置: 第4章「4.6 Network パネルで Form Data を見る」
- 撮影対象: 入力済みフォームを送信した `POST /movies` の `Payload`
- 画面に含めるもの: 選択中の `POST /movies`、`Form Data`、`title`、`director`、`year`、`genre`、`description`
- 伝えること: 入力欄の `name` が送信データのキーになり、入力内容が値になること
- 注釈: フォーム画面と Payload を左右に並べ、同じキーを同じ番号で対応させる
- 理由: HTML の属性、ブラウザの送信内容、Sinatra の `params` のつながりは、初学者が混同しやすい

### 6. 入力エラーでも入力内容が残る

- 掲載位置: 第5章「入力済みの値をフォームに戻す」
- 撮影対象: タイトルを空欄にし、ほかの項目を入力して送信した後の登録画面
- 画面に含めるもの: エラーメッセージ、空欄のタイトル、保持された監督・公開年・ジャンル・紹介文
- 伝えること: エラー時は保存やリダイレクトをせず、入力値を保持して同じフォームを返すこと
- 注釈: 「エラー」「保持された値」の二点だけを示す
- 理由: 正常系だけでは、再表示用の `@movie` を用意する理由が伝わりにくい

### 7. 一覧画面と詳細画面の役割の違い

- 掲載位置: 第6章「詳細画面を表示する」または「一覧から詳細へ移動する」
- 撮影対象: 映画一覧と、そこから開いた一件の詳細画面
- 画面に含めるもの: 一覧側のタイトル・公開年・ジャンル・詳細リンク、詳細側の監督・紹介文を含む全項目、両方の URL
- 伝えること: `/movies` は集合、`/movies/:id` は一件を表し、画面ごとに情報の役割が違うこと
- 注釈: 二画面を左右に並べ、URL の違いを強調する
- 理由: URL 設計をコードだけでなく、実際の画面遷移として理解できる

### 8. 編集・削除までそろった詳細画面

- 掲載位置: 第7章「詳細画面から削除する」
- 撮影対象: 第7章完成時点の映画詳細画面
- 画面に含めるもの: 映画情報、「編集する」リンク、「削除する」ボタン、一覧へ戻る導線
- 伝えること: 読者が実装した CRUD 操作の入口が、どの画面にそろったか
- 注釈: 編集と削除の入口を短く示す
- 理由: 複数節に分けて追加した操作を、一つの完成画面として把握できる

### 9. `_method=patch` と Sinatra の PATCH の対応

- 掲載位置: 第7章「Network タブとログで確認する」
- 撮影対象: 更新フォーム送信時の Network パネルと、同じ操作の Sinatra ログ
- 画面に含めるもの: Network 上の `POST /movies/:id`、Form Data の `_method=patch`、ログ上の `PATCH /movies/:id`
- 伝えること: ブラウザが送る POST と、method override 後に Sinatra が処理する PATCH を分けて読むこと
- 注釈: 三箇所を順に 1、2、3 で結ぶ
- 理由: 第7章で最も混乱しやすい対応であり、文章だけでは二つのメソッドが矛盾して見える

### 10. PRG の三段階

- 掲載位置: 第8章「登録後の流れを見る」
- 撮影対象: 映画登録成功時の Network パネル
- 画面に含めるもの: `POST /movies`、`303 See Other`、`GET /movies/:id`、リダイレクト先を示す `Location`
- 伝えること: Post、Redirect、Get が時系列で起きていること
- 注釈: リクエスト一覧の該当行へ「Post」「Redirect」「Get」を順番に付ける
- 理由: PRG は章の中心概念であり、実際の時系列が一枚で見えると再読み込み時の説明も理解しやすい

### 11. エスケープ前後の比較

- 掲載位置: 第9章「安全な状態で入力してみる」から「危険な表示を一時的に作る」
- 撮影対象: 同じ入力を安全なコードと、一時的に `h` を外したコードで表示した比較
- 画面に含めるもの: 入力文字列、安全な表示結果、HTML として解釈されて崩れた表示結果
- 伝えること: 保存データが同じでも、表示時の扱いによって安全性と画面が変わること
- 注釈: 「入力」「安全な表示」「危険な表示」の三段構成にする。危険な状態はローカルの一時変更だけで撮影する
- 理由: XSS を抽象語だけで終わらせず、エスケープが必要な理由を視覚的に確認できる

### 12. 専用404ページとHTTPステータス

- 掲載位置: 第10章「404 は『見つからない』というレスポンス」または「存在しない URL を扱う」
- 撮影対象: 存在しない映画 ID を開いたブラウザと Network パネル
- 画面に含めるもの: 専用404ページ、存在しない URL、Network の `404 Not Found`
- 伝えること: 見た目としてエラーページを表示することと、HTTPで404を返すことの両方が必要であること
- 注釈: 画面の404表示と Network の Status Code を一本の線で対応させる
- 理由: 画面に「見つかりません」と書くだけで404になる、という誤解を防げる

### 13. 問題を三つの場所で追う

- 掲載位置: 第11章「`params` と JSON ファイルを見る」
- 撮影対象: 一回の登録操作について、Network の Form Data、Sinatra ログ、`data/movies.json` を並べたもの
- 画面に含めるもの: 同じタイトルを示す Form Data、ログの POST とステータス、JSON に保存された一件
- 伝えること: 「送られた」「処理された」「保存された」を別々の事実として確認する切り分け方
- 注釈: 左から「ブラウザ」「Sinatra」「保存先」とし、同じ値を同じ色ではなく同じ番号で示す
- 理由: 第11章の診断方法を一枚で俯瞰でき、どこから調べるか迷いにくくなる

## 優先度 B: 理解を補強するために追加したい

### 14. 最初のSinatraアプリが表示された状態

- 掲載位置: 第2章「2.6 Puma で Sinatra アプリを起動する」
- 撮影対象: `http://localhost:4567/` に「映画図鑑を作ります」と表示されたブラウザ
- 伝えること: 起動成功時に何が見えればよいか
- 判断: 初学者向けには有効。ただし画面が単純なので、本文の出力例で十分なら省略できる

### 15. CSS追加前後の映画一覧

- 掲載位置: 第3章「3.8 最小限の CSS を追加する」
- 撮影対象: 同じ一覧のCSS適用前と適用後
- 伝えること: HTMLの内容を変えず、CSSが読みやすさを変えること
- 判断: HTMLとCSSの役割に不慣れな読者が多い場合に採用する

### 16. 登録成功後に詳細画面へ移動した状態

- 掲載位置: 第6章「登録後は詳細画面へ移動する」
- 撮影対象: 入力済み登録画面と、登録直後の詳細画面
- 伝えること: 作成されたIDを使ったURLへ移動し、送信内容が保存・表示されたこと
- 判断: 優先度Aの一覧・詳細比較やPRGのキャプチャと重複する場合は省略する

### 17. 削除時の method override

- 掲載位置: 第7章「Network タブとログで確認する」
- 撮影対象: `_method=delete` を含むPOSTと、ログ上のDELETE
- 伝えること: 更新時と同じmethod overrideが削除にも使われること
- 判断: `_method=patch` のキャプチャを理解できれば類推可能なので、紙面に余裕がある場合だけ採用する

### 18. 404と500の見分け方

- 掲載位置: 第10章「404 と 500 の違い」
- 撮影対象: 404のNetwork行と、意図的な例外による500のNetwork行・ターミナルログ
- 伝えること: 見つからない状態とサーバー内部の例外では、最初に見る場所が違うこと
- 判断: 第11章の診断キャプチャへ統合できるなら省略する

### 19. 映画図鑑の完成画面一覧

- 掲載位置: 第10章「映画図鑑の完成状態を確認する」
- 撮影対象: 一覧、登録、詳細、編集、404の小さなサムネイル一覧
- 伝えること: 第2章から積み上げた完成範囲と各画面の関係
- 判断: 各章の完成画面を十分掲載する場合は不要。章末や紹介ページで全体像を振り返る場合に採用する

## 撮影しないもの

- `bundle install`、Puma起動ログ、ファイル内容など、本文のコードブロックで正確に示せるもの
- コード全体のスクリーンショット
- 装飾目的だけのブラウザ画面
- 同じNetworkの流れを、登録・更新・削除についてほぼ同じ構図で三枚並べたもの
- Chromeの細かなボタン配置だけに依存する操作説明

## 統一する撮影条件

- Chromeの表示言語は日本語または英語のどちらかに統一し、本文の項目名と併記する
- ブラウザ幅、ズーム率、DevToolsの配置と幅を全キャプチャでそろえる
- OSのメニューバー、ブックマーク、拡張機能、ユーザー名、ローカルの不要なパスを写さない
- 映画データ、ID、入力文言を章間で統一し、同じ操作の続きとして追えるようにする
- 注釈は色だけに依存せず、番号、枠、矢印、短いラベルを併用する
- キャプチャには本文と同等の情報を持つ `alt` を付け、重要な値はキャプションまたは本文にも書く
- Chrome更新で表示が変わっても差し替えやすいように、元画像、注釈前画像、撮影条件を残す
- 画像ファイル名は `capture-<章>-<連番>-<短い内容>.png` の形式にする

## 制作順

1. 優先度Aの1、2、5、9、10、12、13を先に作り、DevToolsの見せ方を確定する。
2. 優先度Aのアプリ画面4、6、7、8、11を章ごとの完成コードから撮影する。
3. 第3章の3を撮影し、HTMLとCSSの行が小さすぎないか確認する。
4. 本文へ仮配置し、スマートフォン幅でも注釈と文字を読めるか確認する。
5. 重複するキャプチャを削り、必要なら優先度Bから補う。
