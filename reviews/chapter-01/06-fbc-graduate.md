# 総評

Sinatra の DSL を先に暗記させず、HTTP の境界から始める構成は、後に Rails を学ぶ際にも役立ちます。特に、ブラウザが Ruby コードを実行しているのではないこと、URL が物理ファイル名ではないこと、画面とレスポンス本文が同じではないことは、実務での障害調査にもそのまま使う考え方です。第1章として難しすぎる内部実装は混ざっていません。

# 良い点

- Network パネルを第1章から使い、以後も観察する習慣の起点を作っている。
- ローカル環境でもブラウザとサーバーは別の役割を持つことを説明している。
- HTTP/1.1 の表示例と、実際の HTTP/2・HTTP/3 の転送形式を混同していない。
- 静的配信と動的生成を「HTML 対 Web アプリ」という誤った対立にしていない。
- 映画図鑑の処理が、一覧、詳細、登録、編集、削除へ自然に分かれている。
- 次章で `get` をリクエストとレスポンスの対応として読ませる橋渡しが明確である。

# 改善が必要な点

## must

### 原稿より先の `app.rb` を第1章の状態から外す

- 対象: `app.rb`, `README.md:33-39`, `manuscript/part1/chapter1.md:147`
- 問題: 第1章ではコードを書かないのに、リポジトリには第2章で導入するはずのルートとリダイレクトが存在します。
- 理由: 初学者はリポジトリの現状を正解として読みます。本文より先のコードがあると、章ごとの変更点と完成状態を追跡できません。
- 修正案: `app.rb` と起動案内は第2章の執筆時に追加する。技術スタックの検証コードは読者用アプリと分けたままにする。

## should

### 404 をサーバー側の判断として書く

- 対象: `manuscript/part1/chapter1.md:109`
- 問題: 存在しないページなら自動的に 404 になるように読めます。
- 理由: 実務でも、エラー画面を表示しながら 200 を返してしまう不具合があります。ステータスコードを適切に返すのは実装の責任です。
- 修正案: 「見つからないことを伝えるために 404 を返す」とし、第10章の実装へつなげる。

### Network 観察の対象条件を固定する

- 対象: `manuscript/part1/chapter1.md:151-159`
- 問題: `file://`、キャッシュ、DevTools を開くタイミングによって、見える内容が変わります。
- 理由: 観察結果が揃わないと、初学者は自分の環境か理解のどちらが原因か判断できません。
- 修正案: HTTP(S) で開いた本書ページを使い、DevTools を開いてから再読み込みする理由を現在の説明と一緒に明示する。

## could

### Protocol 列は後の観察候補に残す

- 対象: `manuscript/part1/chapter1.md:111-113`
- 改善案: 本章では追加しない。全章の横断レビュー時に、HTTP/1.1 の例と実通信の差を質問された場合だけ、Network パネルの `Protocol` 列を「さらに学ぶ」へ加える。
- 期待される効果: 初学者の負荷を増やさず、実際の通信との差を自分で確認する導線を用意できる。
